# 个人开发者环境能力指南：从公司写代码，到真正掌控自己的开发环境

很多程序员在公司里写代码没问题，甚至业务能力很强。

但是一旦离开公司环境，想自己从 0 搭一个可访问、可部署、可运维、可恢复的服务，就会发现很多能力其实是缺失的。

在公司里，很多事情是被平台团队、运维团队、网络团队、安全团队、CI/CD 平台和内部工具链兜底的：

- 代码仓库有人搭好了
- CI/CD 有人搭好了
- 数据库有人申请好了
- 域名、证书、网关有人处理好了
- 日志、监控、告警有人配置好了
- 服务器、安全、权限有人维护好了
- 大模型、内部工具、代理网络也可能有人统一配置好了

所以很多开发者长期只负责“写业务代码”，但不具备独立掌控完整环境的能力。

我最近为了成为一个更专业的个人开发者，系统性搭建了自己的开发环境，包括：

- 本地开发环境
- 海外廉价 VPS
- 回国高速网络 VPS
- LLM 渠道
- LLM 工具链
- 前后端技术栈
- Docker 容器化部署
- Coolify 部署平台
- Cloudflare 域名、DNS、R2 存储
- New API 大模型统一网关
- VitePress + GitHub 个人博客

这篇文章不是商业化教程，也不是教你怎么赚钱，而是分享一个更基础的问题：

> 个人开发者应该如何拥有自己的环境主权？

这里的环境主权，不只是“会写代码”，而是：

> 给我一台电脑、一台 VPS、一个域名、一个 GitHub 仓库、几个模型 API 和一套远程开发工具，我就能独立完成开发、部署、访问、备份、监控、排障和文档化。

我把它拆成十个主题。

严格说，“回国高速网络 VPS 层”可以归入“网络与访问层”，但对中国开发者来说这个话题非常现实，所以我单独拎出来写。

---

## 一、设备与本地环境层

这一层解决的是：

> 我在自己的电脑上，能不能不依赖公司环境，独立完成开发、调试和 AI 辅助编程？

我的本地 PC 主要工具是：

- Docker Desktop
- Cursor
- Codex
- Git
- SSH
- 浏览器
- 本地终端
- 必要的包管理工具

如果是个人开发者，本地环境不需要一开始搞得特别复杂。核心是保证几件事：

1. 能快速拉代码
2. 能快速启动项目
3. 能用 Docker 跑数据库、Redis、依赖服务
4. 能通过 SSH 管理自己的 VPS
5. 能用 AI 工具辅助开发和排障

我的当前习惯是：

- 本地用 Cursor 做主要编辑器
- 本地用 Codex 辅助写代码、改代码、读项目
- Docker Desktop 负责本地容器环境
- VPS 上也安装 Git，方便直接拉代码、改代码、提交代码
- VPS 上也安装 Codex CLI，用来辅助远程开发和运维
- 很多时候我会直接在 VPS 上进行 vibe coding
- 也可以用 Cursor Remote 连接到 VPS，在远程环境里开发
- 需要远程运维时，通过 SSH 登录 VPS，让 Codex CLI 辅助排障、改配置、看日志

这样本地 PC 和远程 VPS 就不再是割裂的两个环境，而是一套可以被 AI 工具串起来的开发系统。

我现在越来越觉得，个人开发者不一定所有代码都要在本地写。有些项目本来就是部署在 VPS 上，依赖环境、数据库、容器、网络都在服务器侧，直接远程开发反而更接近真实运行环境。

所以我的工作流大概是：

```text
本地 PC
  ├── Cursor
  ├── Codex
  ├── Docker Desktop
  ├── Git
  └── SSH

VPS
  ├── Git
  ├── Docker
  ├── Codex CLI
  ├── 项目代码
  ├── 数据库
  └── 真实部署环境
```

简单项目可以在本地开发后推到 GitHub，再由 Coolify 部署。

更偏运维、部署、服务器环境相关的项目，我会直接在 VPS 上 vibe coding，用 Codex CLI 或 Cursor Remote 辅助开发。

如果没有 ChatGPT / Codex 生态，也可以考虑 OpenClaw 这类自托管 Agent 框架。但要注意，OpenClaw 不是模型本身，也不是 GPT 账号的直接替代品，它更像是一个自托管的 Agent 控制层，通常仍然需要配置可用的大模型 API。

## 二、服务器与系统层

这一层解决的是：

> 我能不能自己买服务器、初始化服务器、管理服务器，并让它稳定跑起来？

个人开发者最常接触的是 VPS，也就是虚拟云服务器。

我目前把 VPS 分成四类：

| 类型 | 主要用途 |
|---|---|
| 海外廉价 VPS | 跑项目、跑数据库、部署个人服务 |
| 回国高速网络 VPS | 做代理、跳板机、API 中转、远程访问加速 |
| 国内大厂云服务器 | 面向国内用户的合规服务 |
| 海外大厂云服务器 | 企业级可靠性更强，但个人成本高 |

### 1. 海外廉价 VPS 怎么选

如果是为了省钱买小资源机器，我最关注的第一个指标是：**内存**。

原因很简单：

> 小机器一般 CPU 够用，最先爆的往往是内存。

尤其是你跑 Docker、数据库、Next.js 构建、Coolify、New API、监控服务的时候，1GB 内存很容易紧张，2GB 起步会舒服很多。

我的经验是：

- 海外廉价 VPS 普遍比国内云服务器便宜
- 海外 VPS 带宽和流量通常更宽松
- 海外 VPS 对接 GitHub、Docker、LLM API、国际服务更顺畅
- 国内云服务器带宽和流量偏贵，而且公开网站涉及备案
- 海外大厂云如 AWS、GCP、Azure 能力强，但对个人开发者来说成本偏高

所以从价格和自由度看，大致是：

```text
海外廉价 VPS < 国内大厂云 < 海外大厂云
```

当然，这里的比较主要面向个人开发者和小项目，不代表企业生产环境的 SLA 选择。

### 2. Contabo 和 RackNerd 怎么选

我目前比较关注的是 Contabo 和 RackNerd。

它们都属于海外廉价 VPS 里比较常见的选择，但定位不太一样。

#### Contabo

Contabo 的特点是：

- 内存大
- 磁盘大
- 价格低
- 欧洲区性价比高
- 适合跑资源型服务

比如你需要：

- 多一点内存
- 大一点磁盘
- 跑数据库
- 跑对象缓存
- 跑多个 Docker 容器
- 跑个人后台服务

那 Contabo 欧洲区很适合。

但是 Contabo 的缺点也要知道：

- 美区通常要加价，我个人不太推荐
- 网络质量不是它的最大优势
- 回国网络一般
- 日常从国内直连开发可能会卡
- 更适合作为“资源型服务器”，而不是“高速网络服务器”

所以我的判断是：

> 需要内存和磁盘资源时，优先考虑 Contabo。

#### RackNerd

RackNerd 的特点是：

- 黑五、元旦前后的新年大促很便宜
- 美国区线路体验通常比 Contabo 更好一些
- 回国网络一般比欧洲 Contabo 更合适
- 适合在大促时买年付小鸡

但是 RackNerd 也有问题：

- 非促销时期价格不一定划算
- 通常是小资源 VPS
- 内存和磁盘性价比不如 Contabo
- 真要跑资源型服务，不一定合适

所以我的建议是：

> RackNerd 最适合在黑五或新年大促时买一台年付机器，价格接近 Contabo 时非常值得；其他时候如果价格偏贵、资源又小，就没必要强买。

### 3. Hetzner

除了 Contabo 和 RackNerd，我还推荐关注 Hetzner。

Hetzner 的特点和前两者不太一样。

它不一定是月付价格最低的廉价 VPS。单看月付价格，Hetzner 可能会比 Contabo 贵不少，资源也没有 Contabo 那么“量大管饱”。

但 Hetzner 的优势是：

- 按小时计费
- 按月结算
- 费用有月度封顶
- 可以临时创建测试机器
- 用完可以销毁
- 适合短期实验、临时测试、跑一次性任务
- 欧洲机房体验不错
- 产品体验和控制台比较现代化

这点对个人开发者很有用。

比如你只是想临时测试：

- 一个新项目部署
- 一个 Docker Compose 服务
- 一个数据库迁移流程
- 一个大资源构建任务
- 一个短期爬虫或批处理任务
- 一个 Coolify 部署实验
- 一个新技术栈 Demo

那 Hetzner 就比年付机器灵活很多。

RackNerd 和 Contabo 更像是：

> 买了长期持有，用来长期跑服务。

Hetzner 更像是：

> 要用时临时开，用完删掉，按小时付费，月度封顶。

所以我会把 Hetzner 定位成个人开发者的“临时实验云”。

它不是最便宜的长期资源池，但非常适合快速开机器、测试、销毁，避免为了一个短期实验又多买一台年付 VPS。

### 4. 国内 VPS

国内我暂时主要看阿里云和腾讯云。

原因很简单：

- 大厂稳定性更有保障
- 生态完整
- 备案、域名、对象存储、数据库、CDN 都能一站式处理
- 没有便宜太多的情况下，我暂时没有必要去折腾太多小厂

国内服务器的问题也明显：

- 带宽贵
- 流量贵
- 公开服务需要备案
- 很多资源不像海外廉价 VPS 那样“量大管饱”

但如果你的目标用户主要在中国大陆，国内服务器仍然是绕不开的选择。

### 5. VPS 选择总结

可以简单总结：

| 场景 | 推荐 |
|---|---|
| 要大内存、大磁盘、低成本长期跑服务 | Contabo 欧洲区 |
| 要美国机房、网络略好、黑五低价年付 | RackNerd |
| 要临时测试、短期实验、按小时使用 | Hetzner |
| 要回国优化、高速网络 | DMIT / Bandwagon 这类优化线路 |
| 要国内合规访问 | 阿里云 / 腾讯云 |
| 要企业级云能力 | AWS / GCP / Azure |

### 6. 新 VPS 的必要初始化

刚买到一台 VPS 后，我建议至少做这些：

- 安装 Git
- 安装 Docker
- 配置 SSH 密钥登录
- 开启 Swap
- 检查或开启 BBR
- 配置基础防火墙
- 设置时区
- 安装常用命令行工具
- 配置基础监控
- 记录服务器用途、IP、端口、域名和服务

其中 Swap 很重要。

很多小内存机器不是 CPU 不够，而是内存不够。没有 Swap 的情况下，跑 Docker、数据库、构建任务时很容易直接 OOM。

SSH 密钥登录也很重要。个人开发者的服务器经常暴露在公网，弱密码和默认 root 登录是很危险的。

## 三、回国高速网络 VPS 层

这一层解决的是：

> 我在海外开发，或者使用海外服务时，如何改善访问中国网络、远程服务器、API 的体验？

这里我单独拎出来讲，是因为它和“普通 VPS”不是一类东西。

普通廉价 VPS 追求的是：

- 内存
- 磁盘
- 价格
- 跑项目能力

回国高速网络 VPS 追求的是：

- 线路
- 延迟
- 丢包
- 稳定性
- 跨境访问体验

这种机器资源往往很小，但是网络贵。

我的原则是：

> 高速网络 VPS 不要拿来跑重服务，主要用来做代理、跳板机、API 中转和远程访问加速。

我个人比较推荐 DMIT。

比如 DMIT 的 LAX.Pro.TINY 这类型号，资源大概是 1C2G，月流量 1000G，价格约 9.9 美元一个月或 88 美元一年。这个价格只是我购买或观察时的价格，后续可能变化。它不是为了跑重型服务，而是适合做网络优化用途。

如果追求极致高速网络，也可以看 Bandwagon。但它通常更贵，而且最廉价的套餐可能只有 1C1G，内存太小，跑多了容易爆。

所以我的建议是：

| VPS 类型 | 用法 |
|---|---|
| Contabo / RackNerd | 跑项目、跑数据库、跑服务 |
| Hetzner | 临时测试、短期实验 |
| DMIT / Bandwagon | 做代理、跳板机、API 中转 |
| 国内阿里云 / 腾讯云 | 面向国内用户和备案服务 |

我自己会在高速网络 VPS 上主要部署两类东西：

- 跨境网络优化工具
- 大模型个人中转站，例如 New API 这类统一模型网关

它的定位更偏向网络和模型访问能力，而不是业务承载能力。

所以我一般不会在这类机器上部署业务应用、数据库、缓存等服务，而是把它专门用于跨境网络优化和大模型访问。

## 四、网络与访问层

这一层解决的是：

> 我的服务如何被用户访问？域名、DNS、HTTPS、反代、Cloudflare 应该怎么处理？

很多公司开发者不熟悉这一层，因为在公司里通常由基础设施团队处理。

但个人开发者必须懂：

- 域名是什么
- DNS 怎么解析
- A 记录、CNAME、泛域名是什么
- Cloudflare 小黄云是什么
- HTTPS 证书怎么来
- Caddy / Nginx / Traefik / Coolify Proxy 是什么
- 一个域名如何映射多个服务
- 为什么海外服务器国内访问慢

### 1. Cloudflare

我个人建议海外服务器基本都接入 Cloudflare。

Cloudflare 的作用主要是：

- 管理 DNS
- 开启代理后隐藏源站 IP
- 自动处理边缘 HTTPS
- 缓存部分静态资源
- 缓解部分扫描和攻击
- 让海外廉价机的网站在国内访问不至于太差

但这里有一个边界：

> Cloudflare 小黄云不是万能加速器。

它对这些场景更有效：

- 静态页面
- 图片、CSS、JS
- 普通 Web 页面
- 隐藏源站 IP
- 基础 DDoS 防护

但对这些场景不一定有用：

- SSH
- 数据库连接
- 后台 API 延迟
- 大文件上传
- WebSocket 稳定性
- 源站线路很差的动态服务

所以我的表述是：

> Cloudflare 可以明显改善海外廉价机的 Web 访问体验，尤其是静态资源和普通前端页面，但动态接口和后台操作仍然取决于源站线路、服务器性能和用户网络。

### 2. 中国服务器与备案

如果你用中国大陆服务器面向公网提供网站服务，就要老老实实处理备案问题。

这也是我更喜欢海外 VPS 做开发和个人服务的原因之一：

- 不用备案
- 对接国际服务更方便
- 成本更低
- 网络限制更少

但如果你的用户主要在中国大陆，最终仍然可能需要国内服务器、备案、国内对象存储、国内 CDN。

### 3. Caddy

如果是自己手动部署，我很推荐 Caddy。

Caddy 的优点是：

- 配置简单
- 内存占用低
- 自动 HTTPS
- 反向代理写法清晰
- 很适合个人开发者

常见用途是：

- 反向代理
- 域名映射
- 自动申请 HTTPS 证书

比如你有多个服务：

```text
app.example.com      -> localhost:3000
api.example.com      -> localhost:8000
newapi.example.com   -> localhost:3001
```

Caddy 可以很方便地把这些域名转发到不同端口。

### 4. 泛域名证书和泛解析

如果你频繁创建子域名，可以考虑：

- Cloudflare 配置 `*.example.com` 泛解析
- Caddy 通过 DNS-01 申请泛域名证书

这样你新增一级子域名时，不用每次都单独配置 DNS。

但这里要注意几个点：

1. `*.example.com` 通常只覆盖一级子域名，比如 `a.example.com`
2. 它不覆盖多级子域名，比如 `a.b.example.com`
3. Caddy 申请泛域名证书通常需要配置 Cloudflare API Token
4. Cloudflare 边缘证书和源站证书不是一回事
5. 如果你用 Cloudflare 小黄云，用户访问的是 Cloudflare 边缘；如果你关掉代理，用户会直连源站，源站证书就很重要

### 5. Caddy 和 Coolify 的关系

如果你后面要用这些 VPS 系统化运维项目，那就不急着装 Caddy。

原因不是 Caddy 和 Coolify 天然冲突，而是：

> Coolify 自带 Proxy。如果你又在同一台机器上跑 Caddy，并且两者都想占用 80/443，就会产生端口冲突和反代职责冲突。

所以我的建议是：

- 单机手动部署：用 Caddy 很舒服
- 系统化管理多个项目：优先用 Coolify 自带 Proxy
- 除非你很清楚自己要做前置网关，否则不要让 Caddy 和 Coolify 同时抢 80/443

## 五、AI 工具链层

这一层解决的是：

> 个人开发者如何把大模型变成自己的开发助手、运维助手和知识助手？

我目前的 AI 工具链主要包括：

- ChatGPT Plus
- Codex
- Cursor
- Claude API
- Gemini API
- DeepSeek API
- OpenAI Whisper
- New API
- OpenClaw
- 必要时测试国产模型

### 1. ChatGPT Plus 和 Codex

我个人认为，ChatGPT Plus 对个人开发者很值得。

原因不是单纯为了聊天，而是：

- ChatGPT 的交互体验非常好
- Codex 可以辅助写代码、读项目、改项目
- Codex 权限可以给得比较高，能操作本地机器或远程机器
- Codex 能把 PC、VPS、手机这些环境串起来
- 在手机上远程运维自己的 PC 和 VPS，这个体验非常爽

我没有说 Codex 无限量，但就我个人日常开发和运维体验来说：

> ChatGPT Plus 附带的 Codex 量很足，足够支撑个人开发者的大部分日常 coding 和环境折腾。

当然，如果高强度使用，任何套餐都有额度、速率或策略限制，这个要以当时官方页面为准。

### 2. Claude

Claude 的能力很强，尤其是：

- 代码理解
- 长文本理解
- 写作
- 架构分析
- 复杂重构

但 Claude Pro / Claude Desktop 对中国用户不一定友好，支付、访问、上下文窗口体验都可能不稳定。

我的实际使用倾向是：

> Claude 真要用时，用 API 更灵活；单独开 Pro 对我个人价值没那么高。

### 3. Gemini

Gemini 的优势是：

- 便宜
- 多模态能力强
- Flash 模型性价比高
- API 调用成本低
- 适合图片理解、图片生成、视频理解等多模态场景

我个人体验是：

> Gemini Web 版 Pro 对我的提升有限，很多时候和 Flash API 的体感差距没有大到值得单独付费。

但 Gemini 系列在多模态上仍然非常值得用。

所以我的实际策略是：

- 简单、日常、低成本开发辅助：DeepSeek Flash
- 稍微复杂一点的任务：Gemini Flash
- 多模态理解：Gemini 系列
- 生图场景：Gemini 系列
- 语音转文字：OpenAI Whisper
- 更复杂的 coding：Codex / Cursor 内置模型
- 需要 Claude 能力时：Claude API

这里我的体感是：

> DeepSeek Flash 适合便宜、稳定、日常辅助；任务复杂一点时，Gemini Flash 更值得切换；涉及多模态和生图时，Gemini 系列更方便；语音转文字则用 OpenAI 的 Whisper。

### 4. DeepSeek 和国产模型

我买过字节的 coding plan，也测试过一些国产模型，比如：

- MiniMax
- GLM
- Qwen
- Kimi
- Doubao

我的个人体验是：

> 虽然网上经常有文章说国产模型已经很强，但我实际用下来，DeepSeek 更中规中矩，也更对得起价格。

其他国产模型不是不能用，而是：

- 有的 API 单独购买价格不低
- 有的 coding 体验不稳定
- 有的文档、兼容性、工具链体验不够顺手
- 有的模型宣传很强，但日常开发体感没有拉开差距

所以我的日常选择很简单：

| 场景 | 模型 / 工具 |
|---|---|
| 日常低成本开发辅助 | DeepSeek Flash |
| 稍微复杂一点的推理、写作、代码辅助 | Gemini Flash |
| 图片理解、多模态输入 | Gemini 系列 |
| 生图 | Gemini 系列 |
| 语音转文字 | OpenAI Whisper |
| 更复杂的代码任务 | Codex / Cursor 内置模型 |
| 需要 Claude 能力时 | Claude API |
| 需要 OpenAI 通用能力时 | OpenAI API |

这个选择不是说某个模型绝对最强，而是从个人开发者角度看：

> 模型要按场景切，不要所有事情都用最贵模型。

简单任务用便宜模型，复杂任务切更强模型，多模态和语音任务用专门能力，这样整体成本最低，体验也更稳定。

### 5. New API

有了各大模型厂商 API Key 后，我建议配置到自己的 New API 里统一管理。

New API 的价值是：

- 统一管理多个模型厂商
- 将不同模型转换成 OpenAI 兼容接口
- 提供 UI 管理
- 资源占用低
- 对个人开发者足够好用
- 方便接入各种支持 OpenAI-compatible 的工具

个人开发者我更推荐 New API，而不是 LiteLLM。

但这里要说清楚场景：

| 工具 | 更适合 |
|---|---|
| New API | 个人开发者、小团队、想要轻量 UI、统一模型入口 |
| LiteLLM | 团队级 AI Gateway、预算控制、复杂路由、企业级策略 |
| 直接配置 API Key | 最简单，但多个工具之间不好统一管理 |

所以我的结论是：

> 对个人开发者来说，New API 更轻、更直观、更适合日常自用；如果你是团队级模型网关，需要复杂路由、预算、观测和权限控制，LiteLLM 仍然值得考虑。

### 6. AI 工具链的整体形态

我的 AI 调用链路大概是：

```text
Cursor / Codex / 自己的应用 / 语音与多模态工具
        ↓
     New API
        ↓
DeepSeek / Gemini / Claude / OpenAI / Whisper / 其他模型
```

这样做的好处是：

- 不同工具只需要配置一个 OpenAI-compatible 地址
- 后面换模型不用到处改配置
- 可以统一看用量
- 可以控制访问密钥
- 可以根据场景切模型
- 语音、多模态、生图、代码任务可以走不同模型

## 六、部署与发布层

这一层解决的是：

> 我写完代码后，如何把项目上线，并且可持续更新和管理？

### 1. 快速 MVP：Vercel + Supabase

如果你是海外开发者，快速做 MVP，最省事的组合是：

```text
Next.js + Vercel + Supabase
```

Vercel 原生支持 Next.js，Supabase 提供 PostgreSQL、Auth、Storage 等能力。这个组合非常适合快速验证想法。

但缺点是：

- 成本可能随着用量上升
- 服务在海外
- 受平台规则限制
- 部分场景不如自己部署自由

### 2. 本地服务器部署：Docker 化

如果是自己部署，我建议所有项目都容器化。

原因是：

- 环境干净
- 好迁移
- 好备份
- 好复现
- 不污染宿主机
- 部署方式统一

自己手动部署时，最基础的方式是：

```text
Dockerfile + docker-compose.yml
```

这已经能覆盖大部分个人项目。

### 3. Coolify

如果你想系统化管理多个项目和多台 VPS，我推荐 Coolify。

Coolify 官方自己的产品描述就是：

> open-source & self-hostable alternative to Vercel, Heroku, Netlify and Railway

所以你可以把它理解成：

> 把自己的 VPS 变成一个类似 Vercel / Heroku / Railway 的自托管部署平台。

它能做的事情包括：

- 部署 Web 应用
- 部署数据库
- 部署一键服务
- 管理环境变量
- 接 GitHub 自动部署
- 管理域名
- 自动配置 Proxy
- 管理 HTTPS
- 配置备份
- 部署到不同 VPS

如果你的项目代码放在 GitHub 上，Coolify 可以识别代码变化，然后自动更新部署环境。

所以我的理解是：

> Vercel 适合快速云托管；Coolify 适合个人开发者把自己的 VPS 变成自托管 PaaS。

### 4. Coolify 和 R2 备份

项目数据备份我使用 Cloudflare R2。

R2 是 Cloudflare 的 S3-compatible 对象存储，可以理解为类似 S3 的对象存储服务。

Coolify 支持接入 S3-compatible storage，所以可以把 Cloudflare R2 配进去，然后用它自动备份数据库。

这一点对个人开发者非常重要。

因为很多人只会部署，但不会备份。

真正专业的判断是：

> 服务能跑只是第一步，数据能恢复才是关键。

所以我建议：

- 数据库定时备份到 R2
- 备份文件保留多个版本
- 不要只备份，不测试恢复
- 至少每个月手动恢复测试一次
- 换 VPS 时，要能从 R2 拉备份恢复

## 七、开发技术栈层

这一层解决的是：

> 我真正做项目时，用什么技术栈比较适合个人开发者？

### 1. Web 项目

目前如果是 vibe coding，AI 最熟悉、训练数据最多、生态最完整的方向之一是：

```text
Next.js + TypeScript + Tailwind CSS + shadcn/ui
```

这个组合的优点是：

- AI 生成质量稳定
- 社区样例多
- Vercel 原生支持 Next.js
- Coolify 也能很好支持 Next.js
- Tailwind CSS 适合快速写 UI
- shadcn/ui 适合快速搭页面
- TypeScript 对 AI 改代码和维护项目更友好

我的默认推荐是：

```text
Next.js + TypeScript + Tailwind CSS + shadcn/ui + PostgreSQL
```

如果要加 ORM，可以选：

- Drizzle ORM
- Prisma

如果要做登录，可以考虑：

- Auth.js
- Clerk
- Supabase Auth
- 自建登录系统

### 2. 数据库

数据库我分两种场景。

#### SQLite

如果是一个非常简单的项目，比如：

- 单机小工具
- 本地工具
- 小型后台
- 低并发个人应用
- 轻量博客系统

可以用 SQLite。

SQLite 的好处是：

- 简单
- 不需要单独部署数据库服务
- 文件即数据库
- 跟项目一起迁移方便

但它不适合所有场景。

如果你要：

- 多实例部署
- 高并发写入
- 多用户复杂业务
- 复杂权限
- 远程访问数据库
- 更可靠的备份和迁移

那还是建议用 PostgreSQL。

#### PostgreSQL

服务化部署数据库的话，我建议主流选择 PostgreSQL。

原因是：

- 稳定
- 通用
- 功能强
- 生态成熟
- Coolify 部署方便
- 迁移和备份方便
- Supabase 也是基于 PostgreSQL 生态

如果是海外数据库托管，可以看 Supabase。

如果是国内数据库托管，就要针对阿里云、腾讯云等平台选择各自的云数据库服务。

### 3. 对象存储

对象存储用于保存：

- 图片
- 附件
- 用户上传文件
- 备份文件
- 日志归档
- 静态资源

海外我推荐 Cloudflare R2。

国内可以用：

- 阿里云 OSS
- 腾讯云 COS

总体上我的感觉是：

> 海外更像是买各类通用资源自己组合；国内更像是阿里云、腾讯云一个平台全家桶，需要适配平台进行开发。

### 4. 远程开发与本地开发的选择

对个人开发者来说，不一定所有项目都要在本地开发。

我现在会按场景选择：

| 场景 | 开发方式 |
|---|---|
| 普通 Web 项目 | 本地 Cursor / Codex 开发，推 GitHub，Coolify 部署 |
| 服务依赖复杂的项目 | VPS 上直接 vibe coding |
| 运维和部署相关项目 | VPS 上 Codex CLI 直接改 |
| 需要完整 IDE 体验 | Cursor Remote 连接 VPS |
| 本地调试前端交互 | 本地 Docker Desktop + 本地浏览器 |
| 接近生产环境排障 | 直接在 VPS 上看日志、改配置、重启服务 |

这种模式有一个好处：

> 本地负责舒适开发，VPS 负责真实环境，AI 工具负责把两边连接起来。

## 八、安全与风控层

这一层解决的是：

> 我自己的环境会不会裸奔？账号、API Key、数据库、服务器会不会被人刷爆？

个人开发者不一定要搞企业级安全，但必须有最低安全基线。

### 1. VPS 安全基线

刚买 VPS 后，我建议至少做这些：

```text
1. 配置 SSH 密钥登录
2. 禁止 root 密码登录
3. 使用强密码或禁用密码登录
4. 配置防火墙，只开放必要端口
5. 数据库不要暴露公网
6. 面板类服务不要裸露弱密码
7. 定期更新系统安全补丁
8. 重要服务不要全部跑在 root 权限下
9. 备份文件不要放在 Web 可访问目录
10. 记录每台服务器的用途、域名、端口和服务
```

最常见的开放端口一般是：

```text
22   SSH
80   HTTP
443  HTTPS
```

数据库端口如 PostgreSQL 的 `5432`，如果不是非常明确需要公网访问，尽量不要暴露到公网。

### 2. API Key 安全

个人开发者现在会接很多 API：

- OpenAI
- Claude
- Gemini
- DeepSeek
- Cloudflare
- GitHub
- Supabase
- R2
- 邮件服务
- 支付服务

这些 Key 一旦泄露，可能造成真实费用损失。

最低要求是：

- 不要把 API Key 写死进代码
- 不要提交 `.env` 到 GitHub
- 使用 `.env.example` 记录变量名
- 使用密码管理器保存重要密钥
- GitHub 仓库开启 Secret Scanning 或类似保护
- 发现泄露后立即 rotate key
- 不同用途使用不同 key，不要一个 key 到处用

### 3. New API 安全

New API 这种模型中转站尤其要注意安全。

因为它背后接的是你的真实模型 API Key，一旦被别人刷，可能直接产生费用。

我的建议是：

```text
1. New API 后台开启双因素验证
2. 管理员密码使用强密码
3. 不要公开暴露后台路径
4. 给不同客户端发不同 token
5. 设置额度限制
6. 设置模型权限
7. 不要把上游 API Key 暴露给客户端
8. 定期查看调用日志和异常用量
9. 有条件可以套 Cloudflare Access 或其他访问控制
10. 发现异常立刻禁用 token
```

如果只是个人自用，New API 更要控制访问范围。不要因为“只是自己用”就把它裸露在公网。

### 4. 账号安全

开发者最重要的账号包括：

- GitHub
- Google
- Cloudflare
- ChatGPT
- Claude
- Gemini
- 域名注册商
- VPS 服务商
- 邮箱

这些账号建议全部开启 2FA。

尤其是：

- GitHub
- Cloudflare
- 域名注册商
- New API 后台
- VPS 服务商

因为它们一旦被拿下，可能直接影响你的代码、域名、服务器和模型费用。

## 九、运维与可靠性层

这一层解决的是：

> 服务上线后，能不能长期稳定运行？挂了我知不知道？炸了我能不能恢复？

很多人会部署，但不会运维。

真正专业的个人开发者至少要掌握：

- 日志
- 监控
- 告警
- 备份
- 恢复
- 迁移
- 成本控制

### 1. 日志

最基础的日志能力包括：

```bash
docker logs
docker compose logs
journalctl
coolify logs
```

你至少要知道：

- 服务为什么启动失败
- 应用报错在哪里看
- 数据库连接失败在哪里看
- 反向代理错误在哪里看
- 磁盘满了在哪里查
- 内存爆了怎么看

### 2. 监控

个人项目最低可以用：

- Uptime Kuma：监控服务是否在线
- Sentry：监控前后端异常
- Netdata：看服务器 CPU、内存、磁盘、网络
- Coolify 自带状态页面和日志

最低监控目标是：

```text
1. 服务挂了我能知道
2. 域名访问异常我能知道
3. 应用报错我能知道
4. 服务器磁盘快满我能知道
5. 内存长期不足我能知道
```

### 3. 备份

备份要覆盖：

- 数据库
- 上传文件
- 对象存储
- 环境变量
- Docker Compose 文件
- Coolify 配置
- 重要脚本
- 域名和 DNS 记录说明

对个人开发者来说，数据库备份最重要。

我的建议：

```text
1. 定时备份 PostgreSQL
2. 备份上传到 Cloudflare R2
3. 保留多个历史版本
4. 备份文件不要公开访问
5. 每月至少做一次恢复测试
6. 写一份恢复步骤文档
```

### 4. 恢复

不要以为“我有备份”就安全了。

真正要问的是：

> 如果这台 VPS 明天炸了，我能不能换一台机器，在一小时内恢复核心服务？

你应该至少准备：

```text
1. 新 VPS 初始化脚本
2. Docker 安装脚本
3. Coolify 重建步骤
4. 数据库恢复命令
5. R2 备份下载方式
6. 环境变量备份
7. Cloudflare DNS 切换步骤
8. 服务启动检查清单
```

会部署只是入门，会恢复才算真正拥有自己的服务。

## 十二、总结

很多开发者在公司里写代码没问题，但离开公司环境后，会发现自己其实不太会：

- 买 VPS
- 初始化 Linux
- 配 SSH
- 在 VPS 上安装 Git、Docker、Codex CLI
- 远程连接 VPS 进行 vibe coding
- 配域名 DNS
- 配 HTTPS
- 理解 Cloudflare
- 容器化部署项目
- 管理数据库
- 备份和恢复
- 查看日志
- 监控服务
- 使用 AI 工具链
- 选择不同模型处理不同任务
- 把经验沉淀成文档和模板

这不是能力差，而是公司环境把这些能力隐藏了。

但如果你想成为专业的个人开发者，就不能只会写业务代码。

你需要拥有自己的环境主权。

我目前把个人开发者环境能力拆成十个主题：

```text
1. 设备与本地环境层
2. 服务器与系统层
3. 回国高速网络 VPS 层
4. 网络与访问层
5. AI 工具链层
6. 部署与发布层
7. 开发技术栈层
8. 安全与风控层
9. 运维与可靠性层
10. 知识资产层
```

严格说，这里不是十个完全并列的“层”。其中“回国高速网络 VPS 层”可以归入“网络与访问层”，“安全与风控层”也横跨服务器、网络、AI 工具链和部署系统。

但作为知识博客系列，这样拆是有意义的。

因为它更符合个人开发者真实会遇到的问题：

- 本地怎么开发？
- 服务器怎么买？
- 网络怎么连？
- 模型怎么用？
- 项目怎么部署？
- 技术栈怎么选？
- 数据怎么备份？
- 服务挂了怎么看？
- 账号和 Key 怎么保护？
- 经验怎么沉淀？

我的核心观点是：

> 个人开发者的第一步，不是商业化，也不是做爆款产品，而是先掌握自己的开发、部署、网络、AI、运维和知识资产体系。

当你能从 0 搭起自己的环境，并且让服务稳定跑起来、能访问、能备份、能恢复、能排障、能沉淀文档时，你就已经和只会在公司写业务代码的开发者拉开了距离。

这里的环境主权不只是“本地能写代码”，还包括：

> 能在自己的 VPS 上直接开发、部署、运维、排障，并用 AI 工具把本地电脑、远程服务器、模型 API 和知识文档连接起来。

这才是我认为个人开发者真正值得补齐的基础能力。
